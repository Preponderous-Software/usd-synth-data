# Concept

## The problem

Perception models for robotics (object detection, instance segmentation, depth estimation)
need large amounts of labelled images. Hand-labelling real photos is slow, expensive and
inconsistent, and some labels (per-pixel depth, pixel-exact instance masks) are close to
impossible to get by hand at all.

Synthetic data sidesteps the labelling problem: when the scene is generated by a program, every
label is known exactly. The hard parts move elsewhere:

1. **Variety.** A model trained on one tidy scene learns that scene. *Domain randomization*
   (randomizing objects, poses, clutter, lighting, materials and camera placement) is the
   standard way to force a model to learn the object rather than the backdrop.
2. **Reproducibility.** When a model misbehaves on a training image, it should be possible to
   regenerate *exactly that image* — same scene, same labels — without regenerating the whole
   dataset or keeping every intermediate file forever.
3. **Throughput.** Path-traced rendering is expensive. A dataset of 100k images is only
   practical if rendering parallelizes cleanly across many machines, and if the cost per image
   is measured rather than guessed.
4. **Interchange.** Scenes locked inside one tool's native file format are hard to inspect,
   diff, or re-render with a different renderer later.

## What usd-synth-data is

A procedural synthetic-dataset generator with three cleanly separated stages:

1. **Generate.** A Python scene generator samples a randomized scene from a declarative
   config and writes it as an [OpenUSD](https://openusd.org/) stage. Every random choice is
   drawn from a seed derived deterministically from `(dataset seed, scene index)`.
2. **Render.** A headless renderer (Blender Cycles by default) loads the USD stage and renders
   RGB plus the auxiliary passes needed for ground truth.
3. **Label.** Ground-truth 2D bounding boxes, instance segmentation masks and depth are derived
   from those passes and written as a COCO-style dataset.

Rendering is sharded: a shard is a contiguous range of scene indices, and each shard runs as
one Kubernetes Job pod on any cluster (or as one local process). Throughput — images per hour,
overall and per stage — is measured on every run and written next to the dataset.

## Who it is for

- Robotics and computer-vision developers who need a labelled dataset for a specific object
  set and environment and do not want to hand-label it.
- Researchers who want a small, readable, reproducible pipeline to run domain-randomization
  ablations (e.g. "does randomizing lighting matter more than randomizing texture?").
- Anyone who wants to see how scene description, rendering and labelling can be kept as
  separate, testable stages with a portable file format between them.

## What makes it interesting

- **USD as the contract between stages.** The generator never touches the renderer; it only
  writes USD. A scene can be opened in any USD viewer (`usdview`, Blender, Omniverse), diffed
  as text (`.usda`), and re-rendered by a different backend later without changing the
  generator.
- **Seed-addressable images.** Any image in a dataset can be regenerated from three values:
  the config file, the dataset seed and the scene index. The dataset manifest records them.
- **Throughput is a first-class output.** Every run reports images/hour and a per-stage time
  breakdown (generate, load, render, label, write), so the effect of a change such as fewer
  samples or a smaller resolution is measured rather than assumed.
- **Runs anywhere.** The default renderer runs on CPU, so the full pipeline works on a laptop
  and in CI; a GPU only makes it faster. The Kubernetes fan-out uses only built-in Job
  features, so it runs on any conformant cluster, including a local `kind` cluster.

## Non-goals

- **Not a physics simulator.** Objects are placed by sampling plus simple rejection tests
  (non-overlap, resting on a support surface). Physically settled piles, articulated objects
  and dynamics are out of scope for the MVP; see ARCHITECTURE.md open questions.
- **Not a training framework.** The output is a dataset on disk. Training and evaluating models
  on it is left to the user's existing tools.
- **Not a photorealism benchmark.** The goal is useful variety and correct labels, not
  matching a particular real camera.
- **Not video or sequences.** One independent still image per scene for the MVP; no optical
  flow or temporal consistency.
- **Not a general USD authoring tool.** It writes the narrow subset of USD it needs.
- **No hosted service.** It is a command-line tool and container images; there is no web UI.

## Prior art

These projects were checked directly (repository metadata and READMEs, October 2026). The
project borrows ideas from all of them; the comparison below is about scope, not quality.

| Project | What it is | License | How usd-synth-data differs |
|---|---|---|---|
| [BlenderProc](https://github.com/DLR-RM/BlenderProc) | "A procedural Blender pipeline for photorealistic training image generation". Mature; loads `.obj`, `.ply`, `.blend`, `.fbx`, BOP, ShapeNet and more; writes HDF5, COCO and BOP annotations. Latest release v2.8.0 moved to Blender 4.2.1. | GPL-3.0 | BlenderProc builds the scene inside Blender with its own Python API. Here the scene is authored as USD outside the renderer, so it is renderer-independent and inspectable on its own. MIT-licensed. Sharding and throughput measurement on Kubernetes are built in rather than left to the user. |
| [Kubric](https://github.com/google-research/kubric) | Google Research pipeline for "semi-realistic synthetic multi-object videos" with instance segmentation, depth and optical flow; built on PyBullet (physics) and Blender (rendering). Its README states it uses Blender 2.93. | Apache-2.0 | Kubric targets video and physics-settled scenes and keeps the scene in its own Python object model. usd-synth-data targets still images, uses USD as the scene format, and tracks a current Blender LTS. |
| [NVIDIA Isaac Sim](https://github.com/isaac-sim/IsaacSim) / [Omniverse Replicator](https://docs.isaacsim.omniverse.nvidia.com/latest/replicator_tutorials/index.html) | USD-native simulation platform with RTX rendering; Replicator provides randomizers, annotators and writers (including `BasicWriter`, `KittiWriter` and `CocoWriter`, per the [Replicator writer docs](https://docs.omniverse.nvidia.com/extensions/latest/ext_replicator/writer_examples.html) and the [scene-based SDG tutorial](https://docs.isaacsim.omniverse.nvidia.com/latest/replicator_tutorials/tutorial_replicator_scene_based_sdg.html)). | Isaac Sim source: Apache-2.0, but its [LICENSE](https://github.com/isaac-sim/IsaacSim/blob/main/LICENSE) states that building or using it requires additional NVIDIA components (e.g. the Omniverse Kit SDK) under a [separate NVIDIA license](https://www.nvidia.com/en-us/agreements/enterprise-software/isaac-sim-additional-software-and-materials-license/). | The closest in spirit (USD + domain randomization + annotators). It requires an NVIDIA RTX-class GPU (see the GPU table in its [README](https://github.com/isaac-sim/IsaacSim#readme)) and pulls in non-open components. usd-synth-data aims for a pipeline that runs on CPU-only machines and generic clusters, with only open-source dependencies. Replicator is kept as a candidate alternative backend (see ARCHITECTURE.md). |
| [Infinigen](https://github.com/princeton-vl/infinigen) | "Infinite Photorealistic Worlds using Procedural Generation" — procedural natural and indoor scenes in Blender. | BSD-3-Clause | Infinigen focuses on procedurally generating the geometry and materials of whole worlds. usd-synth-data focuses on randomizing placement of a given object set and producing detection/segmentation labels at measured throughput. |
| [Unity Perception](https://github.com/Unity-Technologies/com.unity.perception) | Unity package for synthetic perception data. | Apache-2.0 (per its LICENSE.md) | Its README states the project "has been discontinued and is no longer supported by Unity". |

The concrete gap this project targets: a small, MIT-licensed, CPU-capable pipeline where the
scene is an open interchange format (USD), every image is addressable by seed, and distributed
rendering plus throughput reporting work out of the box on any Kubernetes cluster.
